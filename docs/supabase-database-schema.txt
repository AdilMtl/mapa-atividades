# 🗄️ Schema Completo do Banco de Dados Supabase

## 📋 Visão Geral

O sistema utiliza **Supabase (PostgreSQL)** com 3 schemas principais:
- `auth.*` - Tabelas de autenticação (gerenciadas pelo Supabase)
- `public.*` - Tabelas da aplicação
- Triggers e funções automáticas

**Última atualização:** 29/09/2025 (v3.3.1)

---

## 🔐 Schema: auth.* (Supabase Auth)

### Tabela: `auth.users`
Gerenciada automaticamente pelo Supabase Auth.

**Colunas principais:**
```sql
id                  UUID PRIMARY KEY
email               VARCHAR UNIQUE
encrypted_password  VARCHAR
email_confirmed_at  TIMESTAMP
created_at          TIMESTAMP
last_sign_in_at     TIMESTAMP
Não modificar diretamente! Usar sempre supabase.auth.* APIs.

👥 Schema: public.* (Aplicação)
1. Tabela: usuarios
Propósito: Dados principais do usuário (sincronizado com auth.users)
sqlCREATE TABLE public.usuarios (
  id UUID PRIMARY KEY,
  email TEXT NOT NULL,
  nome TEXT NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
Relações:

id deve corresponder a um registro em auth.users.id
Populado automaticamente via trigger handle_new_user()

RLS Policies:
sql-- Permitir INSERT de qualquer fonte (para trigger funcionar)
CREATE POLICY "usuarios_insert" ON usuarios
FOR INSERT WITH CHECK (true);

-- Usuários só veem seus próprios dados
CREATE POLICY "usuarios_select" ON usuarios
FOR SELECT USING (auth.uid() = id);

-- Usuários só atualizam seus próprios dados
CREATE POLICY "usuarios_update" ON usuarios
FOR UPDATE USING (auth.uid() = id);

-- Usuários só deletam seus próprios dados
CREATE POLICY "usuarios_delete" ON usuarios
FOR DELETE USING (auth.uid() = id);

⚙️ Funções e Triggers
1. Trigger: Sincronização Automática de Usuários
Propósito: Quando um usuário é criado em auth.users, automaticamente criar registros em usuarios e profiles
Função: handle_new_user()
sqlCREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path TO 'public'
AS $function$
BEGIN
  -- Inserir em usuarios
  INSERT INTO public.usuarios (id, email, nome, created_at)
  VALUES (NEW.id, NEW.email, 'Usuário', NOW())
  ON CONFLICT (id) DO NOTHING;
  
  -- Inserir em profiles
  INSERT INTO public.profiles (id, full_name, created_at, updated_at, email_notifications)
  VALUES (NEW.id, 'Usuário', NOW(), NOW(), true)
  ON CONFLICT (id) DO NOTHING;
  
  RETURN NEW;
END;
$function$;
Características:

SECURITY DEFINER: Executa com permissões do criador (postgres)
SET search_path TO 'public': Garante acesso correto às tabelas
ON CONFLICT DO NOTHING: Evita erros se registro já existir
Não tem EXCEPTION: Erros vão falhar explicitamente (melhor para debug)

Trigger: on_auth_user_created
sqlCREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_new_user();
Quando dispara: Imediatamente após criar usuário em auth.users
Testado e verificado: ✅ Funcionando em 29/09/2025

2. Trigger: Auto-update de timestamps
Função: update_updated_at_column()
sqlCREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE 'plpgsql';
Triggers que usam:
sql-- Para roi_leads
CREATE TRIGGER update_roi_leads_updated_at 
  BEFORE UPDATE ON roi_leads 
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

🔍 Queries de Diagnóstico
Verificar sincronização de usuários
sql-- Ver status completo de todos os usuários
SELECT 
  au.email,
  au.email_confirmed_at,
  au.created_at as auth_created,
  u.nome as usuarios_nome,
  p.full_name as profiles_nome,
  CASE 
    WHEN u.id IS NULL THEN '❌ FALTA usuarios'
    WHEN p.id IS NULL THEN '❌ FALTA profiles'
    ELSE '✅ COMPLETO'
  END as status
FROM auth.users au
LEFT JOIN usuarios u ON au.id = u.id
LEFT JOIN profiles p ON au.id = p.id
ORDER BY au.created_at DESC
LIMIT 20;
Verificar RLS ativo
sqlSELECT 
  schemaname,
  tablename,
  rowsecurity as rls_enabled
FROM pg_tables 
WHERE schemaname = 'public'
  AND tablename IN ('usuarios', 'profiles', 'atividades', 'authorized_emails')
ORDER BY tablename;
Verificar triggers ativos
sqlSELECT 
  trigger_name,
  event_object_table,
  action_timing,
  event_manipulation
FROM information_schema.triggers
WHERE trigger_schema = 'public'
  OR (trigger_schema = 'auth' AND event_object_table = 'users')
ORDER BY event_object_table, trigger_name;
Verificar funções
sqlSELECT 
  routine_name,
  routine_type,
  security_type
FROM information_schema.routines
WHERE routine_schema = 'public'
  AND routine_name IN ('handle_new_user', 'update_updated_at_column')
ORDER BY routine_name;

⚠️ Avisos Importantes
1. Modificações Manuais

NUNCA modificar diretamente auth.users
NUNCA deletar registros de usuarios sem deletar em auth.users primeiro
Sempre usar APIs do Supabase para autenticação

2. RLS Security

Todas as tabelas public.* DEVEM ter RLS ativo
Policies devem usar auth.uid() para identificar usuário
Service role ignora RLS (usar com cuidado)

3. Triggers

handle_new_user() é crítico para funcionamento do sistema
Se modificar, testar extensivamente
Sempre usar ON CONFLICT DO NOTHING para segurança

4. Foreign Keys

profiles.id → auth.users.id: Se deletar user, profile é deletado (CASCADE)
atividades.user_id → usuarios.id: Se deletar usuário, atividades são deletadas

## 🔧 Funções Administrativas

### public.admin_list_users()
**Propósito:** Listar usuários de `auth.users` evitando bug do `auth.admin.listUsers()`
```sql
CREATE OR REPLACE FUNCTION public.admin_list_users()
RETURNS TABLE (
  id uuid,
  email varchar(255),
  created_at timestamptz,
  last_sign_in_at timestamptz,
  email_confirmed_at timestamptz
) 
SECURITY DEFINER
SET search_path = auth, public
AS $$
BEGIN
  RETURN QUERY SELECT u.id, u.email, u.created_at, u.last_sign_in_at, u.email_confirmed_at FROM auth.users u;
END;
$$ LANGUAGE plpgsql;

GRANT EXECUTE ON FUNCTION public.admin_list_users() TO service_role;
```

**Usado em:** `/api/admin/assinantes` para listar usuários com contas
